01 · Product thesis

先做“知识服务闭环”，再谈医疗 Agent。

对现有“内容与拍摄”能力而言，最近的增长不是凭空做一个问诊机器人，而是把已有内容资产变成能被患者完成、提问、回访的服务。

核心判断

最值得先验证的单位不是“一个回答”，而是 一次被医生认可的患者行动。

✓医生能在原有拍摄流程上少做重复整理，并保留最终审核权。
✓患者不仅观看，还能通过小测、选择题和任务证明自己理解了什么。
✓患者的疑问被结构化，再进入医生可处理的队列，而不是散落在评论区。

对现有 C 端产品的借力方式

把内容生产从“一次性交付”变成“多次复用的内容单元”：长视频 → 短视频 → 互动卡 → 直播提问 → 回放章节 → 患者随访。

↗内容资产：脚本、画面、字幕、证据、问题、版本统一管理。
↗医生资产：医生个人可信度、专科标签与可复用答复库。
↗用户资产：学习进度、理解盲点、提问和后续服务意向。
02 · Jobs to be done

医生、患者、运营各自要的不是同一个 AI。

三端共享同一套内容与知识对象，但每端都只看到与自己责任相匹配的动作。

医生：把一次专业表达，变成一组可信资产。

医生最怕的是“生成得很快，但要花更多时间返工和担责”。AI 的默认动作应当是整理、提问、标注和提醒，而不是替医生放行。

01 / 说清选题简报输入疾病、患者误区、目标人群与禁区。
02 / 拍好脚本 + 镜头生成口播、B-roll、字幕、停顿和互动节点。
03 / 审核证据闸门引用来源、更新时间、风险句和需人工确认项。

医生真正会看的指标

首轮通过率少返工
高风险句命中可追责
同一主题复用率可积累
产品原则：医生是发布者和升级处置者，AI 是内容编辑、互动编排和问题分流助手。

患者：把“看过”变成“我知道下一步怎么做”。

患者不一定需要更长的医学解释，而需要适配当前处境的短内容、可验证的理解和明确的求助边界。

01 / 找到场景入口按疾病阶段、检查前后、用药或家属角色进入。
02 / 互动小测 + 分支识别误解，给出面向行动的解释，不给诊断结论。
03 / 连接问题回流收藏、追问、预约直播或升级真人/医生服务。

患者得到的价值

短内容完成率少焦虑
理解小测正确率会行动
高风险问题升级不耽误
游戏化只奖励学习与完成，不给疾病严重程度、治疗选择或个体风险做排名。

内容/运营：把一场拍摄，运营成可测量的服务。

运营侧需要的是主题排期、版本管理、直播编排和风险复盘，而不是一堆无法追踪来源的 AI 文案。

01 / 规划主题地图按患者旅程拆误区、关键行动和内容空白。
02 / 编排资产流水线同一证据包自动衍生视频、图文、问答与直播卡。
03 / 复盘闭环看板看懂了没有、问了什么、医生是否及时响应。

运营真正会看的指标

主题到发布时间更快
内容资产复用率更省
直播问题解决率更深
先把已有拍摄和内容流程做成可追踪的“内容对象”，再叠加模型能力；否则 AI 只会加快内容堆积。
03 · Loop design

闭环的最小单元：一条内容，五个节点。

患者的互动不是终点；真正的产品价值在于把理解、问题和升级处置连接回医生。

▱
内容医生审核的解释、视频、图文

↗
行动收藏、提醒、任务、预约
☏

✓

04 · Agent architecture

三个 Agent，三个责任边界。

不是一个大而全的医疗聊天机器人，而是按内容、互动和直播责任拆分，减少不可控的自由发挥。

AGENT 01 / AUTHOR

科普编导 Agent

把医生的知识、已有视频和选题意图，整理成可拍、可审、可复用的内容包。

  • 选题 brief 与人群/场景拆解
  • 脚本、镜头、字幕、标题多版本
  • 证据卡、风险句、引用与版本
  • 从长视频切片到互动节点建议
输出：内容包，不是直接发布的医学答案
看安全闸门 →
AGENT 02 / COACH

患者陪学 Agent

围绕一条科普内容，生成轻量的理解确认、任务和个性化复习，但不做诊断和处方。

  • 视频中插入小测、拖拽、判断、分支
  • 根据错题解释“为什么”，不只给答案
  • 学习进度、收藏、问题和提醒
  • 触发红旗词或个体化诉求时升级
输出：理解与行动记录，不是临床结论
看互动样例 →
AGENT 03 / HOST

直播共创 Agent

帮助医生把直播做成一次高密度的公共答疑，并把无法安全自动回答的问题分给真人。

  • 直播前收集与聚类问题、生成流程单
  • 实时字幕、章节、投票和问题队列
  • 回答候选、来源提示、风险分级
  • 回放自动分段，生成后续科普任务
输出：主持辅助与问题队列，不是替医生出镜

05 · Patient experience

游戏式科普，要奖励理解，不要奖励冒险。

示例：患者看完“检查前准备”短视频后，用 30 秒完成一个理解确认。答错不是惩罚，而是得到更好的解释。

KePu · 患者陪学
检查前准备 · 第 2/4 关

先做哪一件事？

看完视频后的理解确认

如果医生要求检查前保持空腹，下面哪项最稳妥？

答对了。不同检查的要求可能不同，关键是以本次检查的医嘱和机构说明为准；不确定时直接联系医护人员。

把“互动”设计成服务入口。

患者每次选择都应能解释一个误区、补一条上下文，或触发下一步服务。不要为了拉长停留时间塞入无关小游戏。

轻量游戏小测、错题复习、情景选择、进度徽章、连续学习。
个性化按疾病阶段、检查/用药节点、家属角色推荐内容，不按敏感病情公开排名。
互动闭环收藏 → 提问 → 医生审核 → 直播/答复 → 生成后续学习任务。
关键体验指标不是“看了几分钟”，而是“理解题正确率是否提高、风险问题是否被及时升级、医生答复是否减少重复解释”。

08 · Build order

先用 3 个试点验证闭环，再扩成平台。

所有阶段都以医生审核和风险升级为硬约束；直播与游戏化是放大器，不是起点。

验证“内容 → 互动 → 回流”

只选一个专病或一个高频检查场景，用已有内容与拍摄能力做最小闭环。

内容科普编导 Agent：brief、脚本、镜头、字幕、来源卡、风险句。
患者互动视频 + 5 道理解题 + 收藏/提问 + 医生审核队列。
验证10 位医生/100 位患者；关注首轮通过率、完成率、问题升级准确性。

把一次内容变成一条内容流水线

把互动单元、患者进度和直播前后流程接到同一个内容对象上。

产品疾病/阶段内容地图、错题复习、问题聚类、直播流程单和回放生成。
系统医生工作台、内容版本、证据与审核记录、消息与权限。
验证看复用率、医生响应 SLA、患者复访、直播问题沉淀率。

再考虑医疗数据和规模化直播

只有在内容服务闭环稳定后，才值得投入更重的院内接口和基础设施。

平台对接患者门户、院内系统、标准化健康对象与机构级权限。
直播多医生、多专病、峰值弹性、内容审核、回放和多渠道分发。
边界任何临床决策相关能力单独立项，补外部验证、审计和责任主体。

暂时不要做什么

不要先做开放式“AI 医生”容易把科普、分诊、诊断和处方混在一个入口里，验证难、责任重。
不要用停留时长当核心价值医疗科普追求理解与安全行动；过度追求时长会激励夸张标题和焦虑内容。
不要直接把患者数据喂给直播问答先做脱敏、权限、告知同意和医生确认，再讨论个体化回答。
不要把游戏排行榜用于病情可以比学习完成，不应公开比较治疗结果、风险或疾病严重度。
09 · Success metrics

用“理解和闭环”替代“流量和热闹”。

指标要能帮助产品做取舍，也要能暴露安全问题。任何单一指标都不应单独成为上线依据。

≤ 1 天选题到首版内容包效率 · 医生/运营
↑ 理解率互动前后小测提升效果 · 患者
100%高风险问题进人工队列安全 · 医生
≥ 3×一次拍摄的资产复用商业 · 内容
10 · Guardrails

产品边界写进交互，不要只写在免责声明里。

医疗科普的信任来自“什么时候能回答”和“什么时候明确不回答”。

四级风险分流

任何 Agent 输出都先经过风险判定；高风险问题不进入自动回答路径。

G0 / 知识定义、原理、检查流程、术语解释，可引用来源后回答。
G1 / 行动一般准备、复习、记录和就医导航，给条件与边界。
G2 / 个体化涉及个人报告、用药、症状组合，要求医生审核或真人服务。
G3 / 紧急红旗症状、自伤/急症、急剧恶化，立即给出急救/就医升级提示。

发布前后的审计链

来源每个医学主张挂来源、日期、适用范围；模型不能自造出处。
审核医生确认内容、风险句和互动答案；版本记录谁在何时改了什么。
交互用户知道自己在学习还是在寻求医疗帮助；升级入口始终可见。
复盘记录拒答、误分流、医生覆盖和患者投诉，用失败样本改规则。
可推翻本方案的证据：如果真实试点显示患者只想要快速问答、医生不愿审核互动题、或者互动后没有更好的理解/服务转化，就应缩小范围，先做内容工具或人工直播工作台，而不是继续扩张 Agent。
